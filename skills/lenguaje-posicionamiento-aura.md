# Skill — Lenguaje de Posicionamiento Aura Studio

## La regla central

Aura no vende herramientas. Vende criterio, arquitectura y resultados.
El cliente paga por saber qué construir, cómo construirlo y que funcione —
no por una licencia de software que podría comprar solo.

Revelar la stack técnica en una propuesta o conversación comercial es el
error más común de quienes vienen del mundo técnico. Hace que el cliente
pregunte "¿y por qué no lo hacemos nosotros?" — una pregunta que no debería
existir si se habla de valor correctamente.

## Vocabulario: lo que nunca se dice vs lo que sí se dice

### En propuestas y conversaciones con el cliente

| Nunca decir | Decir en cambio |
|---|---|
| "Usamos n8n para conectar esto" | "Construimos un módulo de automatización que conecta..." |
| "Con un nodo de OpenAI hacemos..." | "Nuestro motor de análisis de IA procesa..." |
| "Le metemos la API de X" | "Integramos directamente con X" |
| "Instalamos Brandwatch" | "Desarrollamos una solución de social listening a medida" |
| "Esto es fácil de hacer con la herramienta" | "Es una integración que ya dominamos" |

| "Hacemos un webhook que escucha..." | "El sistema detecta automáticamente cuando..." |

| "Con Google Sheets hacemos la base de datos" | "Usamos la base de datos que ya tienen / una base centralizada" |

## Cuándo sí se nombran herramientas

### Herramientas del cliente: siempre se nombran
Si el cliente ya usa algo, se nombra directamente — es su herramienta, no la de Aura.
> "Conectamos con tu HubSpot actual"
> "Integramos con el Google Workspace que ya tienen"
> "Seguimos usando el Excel de pipeline que manejan hoy"

### Herramientas externas de terceros que el cliente debe contratar
Si el cliente necesita pagar por algo que no es de Aura, se nombra y se explica el costo.
> "Para búsqueda de contactos recomendamos Apollo.io — base de datos de +200M perfiles con email verificado. Costo: desde $49 USD/mes, lo contratan ustedes directamente."

### En conversaciones técnicas con el equipo técnico del cliente
Si hay un developer o IT del cliente en la conversación, el nivel técnico puede subir.
Leer el contexto: si preguntan por detalles de implementación, se responde con honestidad técnica.

## Cómo hablar de las capacidades de Aura

### Marco de referencia para describir lo que se construye

En vez de describir herramientas, describir **capacidades** y **resultados**:

**Capacidades que Aura construye:**
- "Un sistema de inteligencia competitiva que monitorea tu industria en tiempo real"
- "Un módulo de generación automática de propuestas que parte de la información del cliente"
- "Una solución de social listening que entrega reportes semanales de sentimiento de marca"
- "Un agente de prospección que identifica señales de compra en empresas objetivo"
- "Un sistema de reporte comercial que se genera solo, sin que nadie lo arme"
- "Un pipeline de creación de contenido visual automatizado"

**Resultados que Aura entrega:**
- "Tu equipo deja de hacer esto manualmente"
- "El reporte llega solo cada lunes a las 8am"
- "Cada propuesta sale lista en minutos, no en horas"
- "El sistema queda documentado y tu equipo puede operarlo"

## Objeciones técnicas — cómo responderlas sin revelar la stack

### "¿Qué tecnología usan?"
> "Usamos la combinación de tecnologías más adecuada para cada caso — el criterio es que funcione, sea confiable y que el cliente no dependa de nosotros para operarlo. Lo que construimos siempre queda documentado."

### "¿Por qué no lo hacemos con [herramienta X]?"
> "Depende de lo que ya tienen y de lo que necesitan. Si [herramienta X] resuelve el problema mejor y el equipo ya la conoce, te lo digo. Lo que hacemos en Aura es evaluar qué tiene sentido construir vs qué tiene sentido conectar — y diseñar el sistema completo."

### "¿Esto requiere que nosotros aprendamos a programar?"
> "No. El sistema queda construido, documentado y listo para que tu equipo lo opere sin conocimiento técnico. Si en el futuro quieren ajustarlo, también queda documentado para que cualquier desarrollador pueda intervenir."

### "¿Pueden integrarlo con lo que ya tenemos?"
> "Sí — antes de diseñar cualquier solución mapeamos lo que ya usan. El objetivo es complementar, no reemplazar lo que funciona."

## Regla de oro

El cliente contrata a Aura porque confía en el criterio.
El criterio es: saber qué construir, cómo construirlo bien, y qué no construir.
Eso no se demuestra nombrando herramientas — se demuestra haciendo las preguntas correctas
y proponiendo la solución más simple que resuelva el problema real.
